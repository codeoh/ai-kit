# ai-kit设计稿 v3：定位修正与结构化输出

> 状态：定位已拍板（2026-10-06），开始实现。  
> 决定：① 定位从"防幻觉"改为"把一次 AI 分析变成可复用的函数"；② `structured` 默认 true，三档降级；③ 7 条规则中英双份；④ 接缝加 `AbortSignal`；⑤ 不做流式；⑥ 不做联网。  
> 背景：v0.1.0 的评审发现宣传口径大于实际交付能力，且实测出3 个会静默产出错误结果的实现问题。

---

## 1. 定位修正：为什么"防幻觉"这个说法要撤掉

v0.1.0 的 README 把"防幻觉"当核心卖点。这在评审里被判定为最大的风险，三条理由：

**1.1 用户没法验证，也不需要理解。** 防幻觉是学术主张。README 里"Counts, amounts and dates are computed by your code and passed in"这句话，实测不成立——把"共 99999 个工单"喂进去，模型答"共 99999 个工单"，`stats` 早就报了 3，库不会拦。用户要读到第3 层才可能发现这件事。一个开源库如果需要用户读源码才能判断它靠不靠谱，那它已经输了。

**1.2 它把库做小了。** "防幻觉"是垂类需求——只有在意幻觉的人才找防幻觉库。而"分析、总结、推荐"这三类真实需求里，幻觉只是副产品，真正的痛点是别的：prompt 散落各处、改一次不知道有没有搞坏别的场景、输出形状每次不同导致下游难写、换个模型要重调。

**1.3 最关键：定位和交付物不匹配。** 实际交付的是"固化流程"——把 prompt、输出契约、踩过的坑、回归测试收拢成一次声明。**即使模型 100% 诚实零幻觉，这个库依然有用**（你仍然需要固化流程、需要引用、需要回归）。反过来说，模型开始编造时，这个库也救不了你。一个不该由库来担保的东西，不该写在库的主张里。

### 1.4 新的定位表述

> 让一次 AI 分析变成一个可复用的函数。声明一次，之后每次调用都得到同样形状的结果。

对应改动：
- README 主打"分析、总结、推荐"三件事，不提"防幻觉"这个词
- `refs` 从"卖点"降为"副产品"：说明它的作用是让每条结论能点回来源，不宣称它能拦住幻觉
- "数字不经模型"改为陈述设计（"数字由你的代码算好塞进去，模型只负责措辞"），不做保证措辞
- 能力表里 `Every claim carries citations` 这类措辞要保证准确——它准确，因为 `refs` 确实只引用存在的 id；但不能延伸成"所以内容可信"

## 2. `structured`：三档降级，而不是"有或没有"

### 2.1 先纠正一个错误说法

评审时我写过"连 L3 都不行就抛错"，这是错的，把两个正交维度混成了一件事：

- **横向：请求里发什么**（三档都能发，没有"不支持"）
- **纵向：结果怎么处理**（三档共用同一套，与约束强度无关）

纯提示词约束（L3）不可能失败——它不依赖任何模型能力，就是把要求写进 system prompt。任何能对话的端点都收得到。降级链是单向且必然终止的：

```
尝试 L1 → 端点不认 response_format/json_schema → 降 L2
尝试 L2 → 端点不认 response_format/json_object → 降 L3
L3 → 一定发得出去，链在此终止
```

**不存在"L3 也失败"的分支。**

### 2.2 三档的实际差异（查证结果，2026-10）

| 档位 | 机制 | 保证什么 | 谁支持 |
|---|---|---|---|
| **L1** | `response_format: {type: "json_schema", strict: true}` | 结构与类型在解码层被保证 | OpenAI 及部分网关 |
| **L2** | `response_format: {type: "json_object"}` | 只保证输出是合法 JSON；**字段名与类型靠提示词** | DeepSeek、DashScope、SiliconFlow |
| **L3** | 纯提示词 + 解析容错 | 无保证，靠重试 | 全部 |

关键事实：**DeepSeek 不支持 `json_schema`**（其final-message 响应里没有文档），只支持 `json_object`。而 v0.1.0 README 里所有示例用的都是 `deepseek-chat`——**主力场景会直接降级**。

L2 最容易被误解：它保证能 `JSON.parse` 成功，但不保证字段名对、类型对。所以 **L2/L3 下 `sanitizeSections` 的软失败逻辑必须原样保留**。

### 2.3 修正"144 行 → 40 行"这个说法

v0.1.0 的 `parse.ts`(46 行) + `guards.ts`(92 行) = 144行容错逻辑。我上一轮说"走json_schema 后能砍到 40 行"，这个数字只在 L1 路径成立。真实情况：

- **L1 路径**：结构错误从解码层被阻止，`extractJson` 的围栏剥离 / 前后截取 / 数组兜底分支不再需要（这三段共约 25 行）
- **L2 / L3 路径**：**一行都不能少**

所以真实收益是：**对OpenAI 用户消灭一整类运行时错误；对 DeepSeek 用户收益有限。** 之前那个"144 → 40"的说法夸大了，明确作废。

### 2.4 `structured` 的语义边界

`structured` **只管发什么，不管怎么处理**。

| 选项 | 含义 | 抛错行为 |
|---|---|---|
| `true`（默认） | 尝试 L1 → 不支持降 L2 → 不支持降 L3 | **不变**，与选项无关 |
| `false` | 只走 L3，请求体不带 `response_format` | **不变**，与选项无关 |

抛错只由结果形状决定（整体不是对象、无法解析 → `SceneStructureError`），这段逻辑三档共用、一个字不改。L1 只是让"整体不是对象"更少发生。

`structured: false` 的存在意义：某些内部代理会拦截未知字段、某些网关对 `response_format` 报错，这时需要彻底关掉整条链。关掉之后"结构错就抛"的行为不变，只是发生概率变高。

### 2.5 能力探测与缓存

第一次调用若带了 `json_schema` 而端点返回 4xx 且错误信息提到 `response_format` / `json_schema`，就把降级结果记在闭包变量里，后续直接走低一档，**不重复试探**。

- 缓存粒度：单个 model 实例
- 已知取舍：若端点是间歇性故障，首次失败后本实例永久降级。手动换`baseURL` 或新建 model 实例可重置
- 已知局限：探测基于错误响应。**对"接受但静默忽略" `response_format` 的端点无法探测**——这类端点表现为 L1 生效但不强制，此时软失败逻辑兜底，不会出错，只是收益为零

### 2.6 schema 推导

不要求用户手写 schema，从 `scene.output` 自动推导（已验证自洽：`required` 与 `properties` 键数一致，`additionalProperties: false` 逐层设置）：

- `sections` → 每键是 `{text: string, refs: string[]}[]`
- `scores` → 每键是 `{score: number, reason: string, refs: string[]}`

`refs` 白名单**三档都保留**——schema 只能约束形状，约束不了"那个 id 是否真实存在于输入里"。这是结构约束和内容约束的边界，v0.1.0 的 `filterRefIds` 一个字不改。

## 3. 实现层三个 P0 的修法

评审实测发现的三个问题，都会静默产出错误结果。

### 3.1 记录级截断，替代字符级截断

**现状问题**：`truncateRecords` 用 `s.slice(0, limit)` 按字符硬切。实测送出的 prompt 尾部是`"body":"xxxxx…[已截断]`，`JSON.parse` 直接报 `Unterminated string`。模型收到的是**语法错误的 JSON**，且完全不知道自己看的是残缺数据——提示词里没有任何说明。同时 refs 白名单用的是**未截断的完整记录**，于是模型看不到 `r17` 之后的记录，不会引用它们。

**修法**：按记录逐条丢弃，保留完整记录，并明确告知模型"N 条未纳入本次分析"。

```
输入记录（共 100 条，以下 40 条）——另有 60 条因长度限制未纳入，请勿推测其内容：
[...]
```

这样模型知道两件事：数据是完整的 JSON、还有它看不见的部分。这直接消除"模型基于残缺数据凭空编造"这条路径。

### 3.2 非法 score 不再静默变 0

**现状问题**：`sanitizeDimensions` 里 `typeofscore === "number"` 不成立时用 0。实测模型返回字符串 `"4"` 被当成 0。而 0 在评分语义里往往是"无关/无风险"——**语义错误的低分被伪装成一个正常的零分**。维度缺失时同样返回 `{score: 0, reason: "", refs: []}`，调用方无法区分"模型给了 0分"和"模型没给出这个维度"。

**修法**：非法或缺失的 `score` 返回 `null`，`reason` 缺失返回空字符串。调用方用 `score === null` 判断"没有有效评分"。

这是 breaking change，但 0.1.0 未发布，现在改成本最低。README 示例与eval 断言需同步。

### 3.3 被剔除的引用要能被看见

**现状问题**：`filterRefIds` 把编造的 id 直接剔除，条目照旧返回。实测一条内容全编造、`refs: ["ghost1","ghost2"]` 的结论，返回为 `{text: "整段都是编造的。", refs: []}`——**销毁了证据，保留了幻觉本身**，且与"合法的无引用条目"结构上完全一样。记录漏写 `id` 字段时整批 refs 静默清空。

**修法**：区分两种情况——模型没给引用（正常）与引用全被剔除（可疑）。后者在结果里留下标记，让调用方能决定要不要展示。`refs: []` 保持原样（这是绝大多数场景想要的简洁形状），额外字段承载"有几条引用被剔除"这个信息。

## 4. 7 条规则中英双份

**现状问题**：`buildSystemPrompt` 里 7 条规则硬编码中文，只有第 1 条动态替换语言名。实测 `lang: "en"` 时，system prompt 长454 字符，其中 **213 个是中文**。对中文用户没问题，但这是个面向国际的开源库——英文用户拿到的是一段中文 system prompt。跨语言指令遵循率会下降。

**修法**：7 条规则做成中英两份，按 `lang` 切换。纯机械工作量，无设计风险。提示词内容不变，只是换语言。

## 5. `AbortSignal` 接入

接缝签名扩展：

```ts
type Model = (req: {
  system: string;
  prompt: string;
  signal?: AbortSignal;   // 可选
}) => Promise<string>;
```

- 现有适配代码`async ({ system, prompt }) => ...` **不用改**（解构忽略多余属性）
- `openai()` 内部把 `signal` 透传给 `fetch`
- 中断语义：**抛 `AbortError`**，由调用方自己处理。不返回"半截结果 + truncated 标记"——那会让调用方无法区分"模型就说了这么多"和"我掐掉了"

与`structured` 的关系：中断会留下未完成的响应，但因为解析发生在响应完整之后，中断路径不会走到解析，所以不产生半截 JSON。

## 6. 明确不做的

**流式**：与 `json_schema` 冲突。流式的前提是边收边处理，但结构化输出的正确形态是收完再解析——中间态的 `{"summary":[{"te` 没有意义。要处理得写增量 JSON 解析器（数百行），而在有 schema 约束的情况下这部分复杂度省不掉。更实际的问题是：分析/总结/推荐场景的输出通常 1000 字左右，3 秒 loading 和逐字 3 秒的体验差异极小。流式真正有价值的是聊天式长文本生成，而 `runScene` 是单轮结构化，明确不服务。**等第一个真实 C 端场景提出这个需求再做。**

**联网**：与定位错配。这个库处理的是"你已经拿到数据之后"的事，联网属于"怎么拿到数据"。加联网会带来一整串新问题（各家搜索 API、超时与失败、缓存、抓回来的脏 HTML、token 成本、结果不可复现导致离线 eval 失效），和"固化流程"没有半点关系。**边界：ai-kit 从"取数"到"出结构化结论"，取数是你的事。**

## 8. 与 v2 设计稿的差异

| 项 | v2 定位 | v3 定位 |
|---|---|---|
| 核心主张 | 防幻觉 | 把一次分析变成可复用的函数 |
| `refs` 的角色 | 核心卖点，防幻觉的主要手段 | 副产品：让每条结论能点回来源 |
| 输出结构 | 提示词约束 + 解析容错 | 结构化约束（L1/L2）+ 容错兜底（L2/L3） |
| 流式 | 未讨论 | 明确不做，等真实需求 |
| 联网 | 未讨论 | 明确不做，取数不属于本库 |
| 场景能力 | 两种输出形状 | 不变（仍是 `sections` / `scores`） |
| 接缝形状 | `({system, prompt}) => Promise<string>` | 加可选 `signal` |

保留不变的（这几项 v2 做得对）：接缝是函数不是接口、只内置 `openai()`、声明一次调用无数次、`defineScene` / `runScene` / `openai` / `evaluate` 四个导出。
